# Reactのstateはただの変数と何が違い、なぜ直接書き換えてはいけないのですか？

## 一言でいうと

React の state は、画面の再描画と結びついた値です。ただの変数は値が変わっても React に気づかれませんが、state は更新されると React が「画面を作り直す必要がある」と判断できます。

## 何がうれしいのか

画面は、今のデータから作られます。カウント、入力欄の値、選択中のタブ、開いているメニューなどは、ユーザー操作によって変わります。

React では、こうした変わる値を state として持たせることで、「今の状態なら画面はこうなる」という形で UI を書けます。これにより、DOM を直接細かく操作するよりも、状態と見た目の対応を追いやすくなります。

## よくある誤解

初心者がつまずきやすいのは、「state も変数なら直接書き換えればよいのでは」という点です。

たとえば配列の state があるとき、配列に直接 `push` しても、React は変更に気づけない場合があります。React は「新しい値が渡されたか」を手がかりに再描画を判断するため、元の配列そのものを変えるより、新しい配列を作って渡す方が基本です。

## 具体例

避けたい例です。

```jsx
items.push("new item");
setItems(items);
```

基本形は次のように、新しい配列を作ります。

```jsx
setItems([...items, "new item"]);
```

これは「元の配列を壊さず、新しい状態を React に渡す」という意味です。

## どう考えると理解しやすいか

state は「画面を作るための材料」であり、`setState` 系の関数は「材料が変わったことを React に知らせる窓口」です。

直接書き換えると、材料の中身だけがこっそり変わり、React に正式な通知が届かないことがあります。だから React では、値そのものを直接いじるより、「次の状態」を新しく作って渡す習慣が重要です。

## 関連用語

- props: 親コンポーネントから渡される値。
- 再レンダー: state や props の変化に応じて、画面の表現を作り直すこと。
- immutable: 元の値を直接変更せず、新しい値を作る考え方。

## 次に知るとよいこと

次は「state の更新はすぐ反映されるように見えないことがある」という点を学ぶとよいです。React は更新をまとめて処理することがあるため、現在の値に基づいて次の値を作るときは、関数形式の更新も重要になります。
